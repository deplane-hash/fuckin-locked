# One-to-one protocol integration gate

## Decision

Use Signal's maintained `LibSignalClient` Swift bindings through its canonical CocoaPods integration. The Podfile pins `v0.105.0` and the FFI checksum used by Signal-iOS at the time of review. The upstream repository has since published newer releases, but Signal-iOS's current primary Podfile still uses this v0.105.0 pin; upgrading must repeat the checksum, API, CI, and legal review. Remote Swift Package consumption is explicitly unsupported, but CocoaPods integration is documented and used by Signal-iOS. Third-party use is unsupported by Signal, and API or binary compatibility may change without notice. Its license is AGPL-3.0-only; distribution requires a legal review and compliance with that license.

The dependency is pinned and connected to the one-to-one message path in `MessagingService.swift`. The app generates a device identity and prekeys locally, publishes only the public bundle, pins the first observed peer identity after an out-of-band fingerprint comparison, encrypts with `signalEncrypt`, and decrypts with `signalDecryptPreKey`/`signalDecrypt`. Signal records, pending peer bundles, and message ciphertext are committed inside the chat-password-protected vault before relay acknowledgement. Service requests use the configured `https://freedomhub.at/fuckin-locked/` path in this checkout and fail closed if it is unavailable. The macOS workflow is the current compilation and simulator-test authority; live two-device delivery, signed-device capture behavior, and independent review remain open. The Python relay is still only a control-plane/ciphertext relay and never receives protocol private keys.

## Voice calls

Calls use the pinned `WebRTC-lib` 155.0.0 CocoaPods distribution. Its podspec states that the framework is built from official WebRTC source without source or binary modifications and is distributed under the WebRTC BSD license; the binary source and license must be re-reviewed when upgrading. The app uses WebRTC's native iOS API for DTLS-SRTP audio and configures `RTCIceTransportPolicyRelay` with exactly one `turns:` server. It does not configure STUN, host candidates, or a direct fallback. The relay returns the TURN-over-TLS endpoint only after an authenticated session and only advertises `encrypted_calls_v1` when all deployment values are present. The client also rejects a TURN host different from the configured gateway host.

Offer, answer, ICE candidate, and hangup records are `CallSignal` values encrypted by the existing libsignal session. Received records are stored inside the chat-password-protected vault; outgoing call commands persist the advanced ratchet but never enter the message retry outbox. Encrypted commands expire after 90 seconds. The server sees only ordinary opaque envelope metadata and cannot read SDP, candidates, or audio. The authenticated TURN endpoint generates five-minute coturn REST credentials from a server-only shared secret. See [server setup](calls-setup.md) and `deploy/coturn.conf.example`; no live deployment is implied. `AVAudioSession` uses the iOS `playAndRecord`/`voiceChat` configuration. Incoming offers require explicit Accept before creating media resources or requesting microphone permission. Calls stop synchronously with vault locks, including inactive/background and capture responses, and stop when authenticated gateway polling fails.

`WebRTC-lib` is a practical community binary distribution rather than an official Google-maintained CocoaPod. It is pinned to an exact version and should be replaced or rebuilt from a reviewed source if the deployment's supply-chain policy requires that. The CI build verifies compilation and protocol/vault tests; a two-device encrypted-media test, TURN certificate/credential rotation, and independent security review are still required before enabling a Calls destination.

## Required implementation before enabling send

1. Generate Signal identity, signed prekeys, one-time prekeys, and Kyber prekeys on the device after app and chat unlock. The relay receives only public bundles. Verify signatures using libsignal, not custom cryptography. This one-peer-per-room implementation publishes one bundle at a time and generates a replacement after local one-time-key consumption. Persist a prekey claim ID before requesting a peer bundle; only the same active requester with that ID can retrieve the same consumed public bundle after a lost response. Other requests cannot consume it again. Larger multi-device pools, rotation/retention limits and sustained exhaustion tests remain release work.
2. Persist every protocol record and local identity under the corresponding chat content key, with atomic encrypted-vault replacement. Keep inbound ciphertext on the relay until that chat is unlocked. Do not persist a usable protocol decryption key under the app key alone.
3. Bind each protocol address to a relay device identifier and a stable room. Pin the first observed identity per device, show an out-of-band fingerprint comparison, reject identity changes, and reject envelopes from an unexpected relay device. A server-supplied first identity is not by itself authenticated.
4. Establish sessions with `processPreKeyBundle`, send via `signalEncrypt`, and decrypt with `signalDecrypt` or `signalDecryptPreKey`. Persist the advanced ratchet and exact outgoing ciphertext before upload, and persist received content and protocol state before acknowledgement. Stable device-scoped message IDs make upload retries idempotent; conflicting bytes with the same ID are rejected. The UI calls relay acceptance `Sent` and durable recipient acknowledgement `Delivered`, never a read receipt. The encrypted outbox survives restart; its offline/retry tests must pass in the explicit CI integration scheme before release.
5. The present client explicitly binds one remote device to each chat and compares its fingerprint. Additional devices use authenticated approval with a ten-minute expiry, never historical key transfer or silent retargeting. Revocation stops authorization, terminates sessions, and removes undelivered envelopes/prekeys/claims; retries recheck authorization before returning a previous upload result. Future fan-out must separately encrypt to each explicitly approved device. Revocation cannot erase ciphertext or session keys already obtained by a revoked device.
6. Test two independently installed clients through the HTTPS gateway, including offline delivery, restart, wrong password, identity substitution, prekey exhaustion, replay, concurrent send, revocation, and gateway failure. Check transport logs and relay database for plaintext and keys.
